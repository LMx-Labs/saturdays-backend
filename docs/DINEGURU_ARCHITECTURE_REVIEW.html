Restaurant onboarding

Step 1

Approve

Saturdays vets and approves the restaurant.

Step 2

Provision

Saturdays sends an HMAC-signed restaurant, owner, password and API key.

Step 3

Create tenant

DineGuru creates Restaurant, User, Membership and encrypted connection.

Step 4

Operate

The owner logs into DineGuru immediately. Public signup is not used.

Online order lifecycle

Step 1

Customer orders

Saturdays performs checkout and payment.

Step 2

Webhook

DineGuru verifies HMAC and deduplicates the delivery ID.

Step 3

Native ingest

A confirmed order becomes a DineGuru order and KOT; stock is deducted.

Step 4

Fulfill

Staff prepares, assigns a rider and updates Saturdays.

POS order lifecycle

DineGuru has no cart service. A POS cart is an open Order with draft OrderItem rows. Firing a KOT locks kitchen lines and deducts recipe stock. Checkout records CASH, UPI or SPLIT payment.

Current compatibility gap

The current saturdays_v2 application does not contain the /api/dineguru/v1 partner surface or signed provisioning client expected by DineGuru. Starting both servers is not sufficient to integrate them.

Configuration contract

Shared provisioning secret

SATURDAYS_PROVISION_SHARED_SECRET must match the Saturdays-side secret exactly.

Webhook base URL

SATURDAYS_WEBHOOK_BASE_URL is DineGuru's externally reachable API address.

Per-restaurant API key

Saturdays generates it; DineGuru stores it encrypted and sends it as Authorization: Api-Key.

Menu external IDs

Marketplace lines must retain DineGuru item IDs for native KOT and stock ingestion.

Important gaps and risks

  • 1
    Tenant mismatch. Saturdays uses Merchant → Brand → Branch; DineGuru uses Restaurant as the outlet tenant.
  • 2
    Role mismatch. Saturdays roles must translate to DineGuru's owner, staff and rider roles.
  • 3
    No background worker. Missed webhooks depend on reconciliation before KOT and inventory ingest occur.
  • 4
    Menu mapping dependency. Unmapped marketplace lines are skipped during native ingestion.
  • 5
    Membership authorization. Some checks use a user's global role rather than the active membership role.
  • 6
    Secret rotation coupling. DineGuru's secret protects both JWTs and encrypted Saturdays API keys.
  • 7
    Operational readiness. Rate limiting, metrics, backend CI and frontend automated tests remain incomplete.
  • 8
    Deferred product areas. Floor plans, vendor contracts and subscription-tier billing are unfinished.

Recommended integration direction

Map each Saturdays Branch to one DineGuru Restaurant.

Add a Saturdays adapter containing the partner API, provisioning client, stable external IDs, signed webhook delivery, retry and reconciliation. Keep DineGuru as the source of truth for POS, KOT, recipes, inventory, procurement and restaurant fulfillment. Do not merge the databases or duplicate those domains in Saturdays.
